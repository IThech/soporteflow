# Deuda técnica comprobada

Inspección del prototipo en development. Prioridad según impacto antes de usuarios
reales; estos puntos se documentan, no se implementan en esta pasada.

| Prioridad | Evidencia y limitación actual                                                                                                                                                           | Por qué importa                                                                                                         | Cuándo abordarlo                                                                                                                             |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| ALTA      | `src/lib/auth/demo-session.ts` elige usuarios demo; `DemoSessionSelector.svelte` permite cambiar de identidad. La autorización se ejecuta en cliente.                                   | Un navegador controlado por el usuario no es una frontera de seguridad.                                                 | Antes de cualquier acceso de clientes reales: autenticación y autorización en servidor.                                                      |
| ALTA      | `src/lib/auth/record-access.ts` y `src/lib/incidents/assignment.ts` atribuyen registros sin organización a Nodhouses.                                                                   | La compatibilidad histórica no sustituye claves de tenant obligatorias y verificadas.                                   | Al diseñar la base de datos: migración explícita, restricciones y consultas siempre delimitadas por organización.                            |
| ALTA      | `src/lib/storage/assignment.ts` usa dos claves localStorage y un diario de recuperación; compara valores antes de escribir.                                                             | Reduce pérdidas, pero no ofrece exclusión atómica entre pestañas, copias centralizadas ni durabilidad empresarial.      | Antes de colaboración real: transacciones y control de concurrencia en servidor.                                                             |
| ALTA      | `saveIncidents` en `src/routes/app/+page.svelte` recibe una lista ya mutada por crear/editar/eliminar; si falla, bloquea edición y pide recargar, pero no restaura la lista en memoria. | La pantalla puede mostrar un cambio que no se guardó. El flujo de asignación sí actualiza memoria después del guardado. | Antes de uso operativo real: unificar confirmación de persistencia y recuperación sin perder borradores.                                     |
| ALTA      | `createIncident`, `saveEditedIncident`, `updateIncidentStatus` y `deleteIncident` en la página no generan sus correspondientes eventos; el historial se guarda en localStorage.         | La trazabilidad actual es parcial y modificable localmente, no una auditoría fiable.                                    | Antes de compromisos de auditoría: eventos completos y persistidos desde operaciones autorizadas de servidor.                                |
| MEDIA     | `src/lib/incidents/validation.ts` comprueba estructura y enums, pero admite fechas como cualquier string y referencias como identificadores sin integridad relacional.                  | Un registro estructuralmente válido puede contener destinos inexistentes o fechas no interpretables.                    | Durante el diseño de API/esquemas: validación de entrada, fechas y claves foráneas; conservar compatibilidad histórica mediante migraciones. |
| MEDIA     | Listas de incidencias y catálogos se guardan como JSON sin versión global de esquema; usuarios y equipos proceden de `src/lib/data`.                                                    | Evolucionar modelos o administrar organizaciones requerirá transformaciones reproducibles y configuración persistente.  | Antes de la primera migración a base de datos y de activar organizaciones reales.                                                            |
| MEDIA     | `src/routes/app/+page.svelte` reúne persistencia, categorías, filtros, edición y coordinación de diálogos en más de mil líneas.                                                         | Aumenta el riesgo de acoplar cambios visuales y reglas operativas.                                                      | Extraer gradualmente responsabilidades al incorporar API o nuevos módulos, sin un refactor masivo previo.                                    |
| MEDIA     | `tests/*.test.mjs` prueba helpers con Vite y almacenamiento simulado; `package.json` no incluye un comando de tests ni pruebas de flujos de navegador.                                  | Las regresiones de foco, diálogos, hidratación y cambios encadenados dependen de revisión manual.                       | Antes de producción: comando único, CI y pocos flujos de navegador críticos con datos aislados.                                              |

Las pruebas existentes ya cubren permisos, motivos, colas, escalado, recuperación
y tema. No se propone sustituirlas: deben conservarse y complementarse donde no
alcanzan. La separación conceptual modular se describe en `product-architecture.md`.
